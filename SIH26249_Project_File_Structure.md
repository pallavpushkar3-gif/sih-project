# PS 26249 — complete project structure and file responsibilities

This is the proposed repository blueprint, not an implemented application. Populate the specification files first, then create code files as their modules are implemented. Do not create empty source files just to match the tree. The working repository name below is `fleet-maintenance`; branding can change independently.

Stack: React/TypeScript/Vite; Python/FastAPI; PostgreSQL; Celery/RabbitMQ; PyTorch and classical model baselines; OR-Tools CP-SAT; SimPy. One monorepo and one installable Python application package, shared by API and worker processes.

## 2. Root documents: what each means

| File | Contents to write | Contents that belong elsewhere |
|---|---|---|
| `README.md` | Project overview, current implemented status, links to core documents, setup/verification commands and demonstration entry point. | Detailed research conclusions and all business rules. |
| `intent.md` | Why we are building it; users and pain points; desired outcomes; principles; what success means. | Screen layout, API fields or coding instructions. |
| `scope.md` | Included eight features, excluded capabilities, release boundary, dataset limitations and stretch-feature gates. | Detailed feature behaviour; link to feature specifications. |
| `design.md` | System architecture, service/process boundaries, data flow, key interfaces and links to detailed designs. | Duplicated copies of every screen or database field. |
| `rule.md` | Project-wide engineering rules: units, evidence labels, shared preprocessing, mandatory constraints, model provenance, ownership of business logic and required validation. | Product vision or an evolving task checklist. |
| `AGENTS.md` | Instructions for coding assistants: required reading, repository map, module boundaries, commands, edit conventions and verification expectations. Reference `rule.md`; do not duplicate its text. | Invented permissions or restrictions on actions already authorized by the user. |
| `CONTRIBUTING.md` | Human team workflow: branches, changes, review, generated files, migrations and integration expectations. | Separate conflicting rules or repeated architecture. |

For project engineering guidance, `rule.md` is the canonical rule source; `AGENTS.md` links coding agents to it. Product intent lives in `intent.md`, scope in `scope.md`, current behaviour in feature specifications, and architecture in `design.md` plus its linked detail. External user instructions and applicable system/tool instructions still govern the assistant. If internal documents conflict, resolve the conflict explicitly instead of silently choosing a convenient one.

Use the exact singular name `rule.md` requested here. Do not also create `rules.md`, `coding_rules.md`, `ai_rules.md`, or `project_intent.md` containing duplicate guidance.

## 4. Code boundaries

| Folder | Owns | Must not own |
|---|---|---|
| `apps/web/src/features/` | Feature-specific screens and user interactions. | Authoritative maintenance rules or fake model outputs presented as real results. |
| `apps/web/src/shared/` | Reusable controls/charts, HTTP access, events and formatting. | A second copy of backend life estimation or reservations. |
| `backend/.../api/` | HTTP validation, dependency wiring, routes and responses. | Training loops or long calculations inside web handlers. |
| `backend/.../domain/` | Shared contracts, units, enums and explicit domain meanings. | FastAPI request objects, ORM sessions or UI logic. |
| `backend/.../services/` | Business workflows, alerts, approvals, reservations and jobs. | Duplicated scientific preprocessing. |
| `backend/.../persistence/` | Database models, queries, transactions and sessions. | UI presentation or optimizer equations. |
| `backend/.../science/data/` | Dataset validation, engine splits and transformations. | Different training/serving implementations of the same transformation. |
| `backend/.../science/prediction/` | Models, training, inference, calibration, explanations and metrics. | Automatically declaring an aircraft airworthy. |
| `backend/.../science/scheduling/` | Constraint formulation, objectives, solver results and baseline comparison. | Reserving stock by itself or overriding mandatory deadlines. |
| `backend/.../science/simulation/` | Scenario events, policies, replications and availability metrics. | Claims that assumptions are measured military operational facts. |
| `backend/.../workers/` | Job execution, dispatch, progress and attempt/result consistency. | Reimplemented application rules different from the services. |
| `backend/.../artifacts/` | Artifact metadata, hashes and access/storage abstraction. | Mixing model weights with source code. |
| `scripts/` | Thin executable entry points importing application packages. | A second application containing duplicated training or planning logic. |

Thin route handlers call services. Services use domain contracts and persistence. Scientific modules accept validated inputs and return typed results; workers orchestrate execution. Persistence models and public contracts have different responsibilities even when some fields overlap. Python API and worker processes import the same installed package.

## 6. Data, configurations and artifacts

- `data/demo/` contains small synthetic fleet/logistics records, clearly labelled with provenance. Its aircraft-to-engine mappings are demonstrator mappings.
- `data/raw/` contains downloaded dataset bytes; do not commit bulk datasets. `sources.yaml` records dataset links, versions/checksums where available, permitted usage and acquisition method.
- `data/processed/` is reproducible output. `data/splits/` holds immutable engine-level split artifacts referenced by experiments; ignoring these in Git does not mean deleting them or regenerating them arbitrarily. Preserve them with hashes in the artifact store.
- `configs/` holds authored experiment/policy parameters. Secrets never belong here. Code validates settings before execution.
- `backend/.../artifacts/` is source code; root `artifacts/` is generated persistent content. The identical term distinguishes storage code from stored files.
- Model manifests identify dataset/split hashes, target definition, transformations, training settings, calibration artifacts and model version. Evaluation outputs refer to that manifest.
- Simulation manifests identify logistics assumptions, policy/model versions and random seeds. Store these with results.
- `.env.example` lists environment variable names and safe placeholders. Actual `.env` files, credentials and session keys are ignored.
- Lockfiles are generated by package managers and committed. Build outputs, installed dependencies, caches and local runtime databases are ignored.

## 7. What belongs in this project

The eight specified features; evidence-linked research; a held-out-engine prediction evaluation; labelled synthetic logistics; a planner preserving mandatory constraints; reproducible simulation comparisons; human plan approval; and restartable jobs with traceable results.

The initial repository should not contain:

| Excluded item | Reason / future gate |
|---|---|
| Separate Rust/Go/Node backend | No measured component currently justifies a second backend language. Revisit after profiling. |
| Next.js rendering server | No established frontend server-rendering requirement. |
| Whole-aircraft physics twin or VR/game engine | Not supported by the available engine data or central workflow. |
| LLM-generated life estimates or authoritative schedules | Numerical prediction and hard scheduling constraints require validated methods. |
| Learned spare-demand forecasting | Requires appropriate demand/procurement history. Implement reservation/lead times first. |
| Cross-system root-cause diagnosis | Requires relevant labels and subsystem interaction evidence. |
| Kafka, Kubernetes or an extra time-series database | Add only when measured deployment/streaming requirements establish a role. |
| Automatic aircraft clearance or military readiness certification | Our simulated engine data and logistics assumptions cannot support it. |
| Copied paper PDFs, unlicensed graphics or private operational records | Cite sources and track acquisition/licensing; do not indiscriminately bundle material. |
| Huge binaries, dataset archives, model weights or generated reports in source control | Preserve these as versioned artifacts with manifests. |
| Multiple files repeating product intent/rules/design | Use canonical documents and links. |

No legal licence file is prescribed yet: choose the repository's licence deliberately rather than inventing an ownership decision. Add a `LICENSE` file once that decision is made. Public release, hosting, account integration and CI configuration are not performed by this blueprint.

## 8. Verification responsibilities

Tests focus on substantive risks: engine-split leakage, identical training/inference transformations, units, mandatory schedule constraints, stock reservation races, stale plan approvals, job restart/deduplication, and reference simulation cases. E2E tests cover the evidence-to-plan workflow, scenario comparison and degraded-data behaviour. Do not add tests that merely repeat trivial implementation details.

CI checks formatting/types/builds, these meaningful tests, contract generation and migrations appropriate to each change. Research benchmark jobs need their dataset/artifact requirements supplied explicitly; they should not silently download large datasets during every pull request.

## 9. Order to populate files with the assistant

1. `intent.md`: agree on users, outcomes and the product promise.
2. `scope.md`: commit to included/excluded capabilities and data boundaries.
3. `docs/product/feature_specifications.md`: define all eight features concretely.
4. `docs/product/acceptance_criteria.md`: define measurable completion.
5. `design.md`: connect frontend/API/workers/database/artifacts and module boundaries.
6. `rule.md`: establish shared units, provenance, constraints and implementation rules.
7. `AGENTS.md`: tell coding assistants exactly how to work in this repository.
8. Research protocols: populate literature/evidence, dataset, evaluation and simulation assumptions using the reviewed sources.
9. Detailed engineering: data model, API contracts, jobs, events and permissions.
10. UI specifications: screens, tokens and interaction states.
11. Team ownership and milestones; then README/setup/contribution instructions.
12. Dependency/configuration files, followed by implementation in dependency order.

Keep documents truthful to the current implementation. A specification describes intended behaviour; README status and reproduction logs describe work actually completed. Generated manifests, clients, lockfiles and migrations are produced by tools when the corresponding implementation exists, rather than filled with guessed content now.
